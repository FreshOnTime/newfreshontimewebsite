# FreshPick Supabase Auth pilot
## Status
Implemented an opt-in server-side REST integration (no additional npm dependency). Supabase manages password verification, confirmation, recovery and refresh tokens. FreshPick uses a ten-minute signed application access cookie as a compatibility bridge to existing authorization; refresh credentials remain Supabase-issued. Prisma preserves application user IDs, maker ownership and roles. Unmigrated accounts keep legacy login. Admin accounts and phone-only accounts remain legacy until MFA and recovery migration are reviewed. Google UI was removed previously; the Google API returns 410 when the flag is enabled. Managed account email changes are blocked pending a verified email-change flow. Do not consider this final removal of legacy authentication.
## Staging setup
1. Use a nonproduction Supabase project and staging database, apply `npx prisma migrate deploy`, and ensure all public-schema tables exposed through the Data API have RLS enabled or revoke client grants/disable the Data API. The existing Prisma server connection must remain authorized. Do not use production data or send real customer emails in CI.
2. Set SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY (or SUPABASE_ANON_KEY), existing DATABASE_URL and JWT_SECRET in the staging deployment. Set FRESHPICK_SUPABASE_AUTH=true only after step 3. The existing storage secret is not used by the normal auth runtime.
3. Supabase Authentication: enable email/password and require confirmation, disable unneeded providers, configure Site URL and exact redirect allowlist, password policy, rate limits, CAPTCHA if required, and custom SMTP (e.g. Resend). Configure a verified sender domain. Do not use default SMTP for production. Disable link tracking for authentication emails.
4. Replace Confirm signup and Reset password templates with the links below. Use the configured staging or production Site URL, not a user-supplied redirect.
   - Confirm signup: `{{ .SiteURL }}/auth/verify?token_hash={{ .TokenHash }}`
   - Reset password: `{{ .SiteURL }}/auth/reset-password?token_hash={{ .TokenHash }}`
5. Test a new member, verification before login, wrong password, expired/used links, reset email delivery, session refresh/logout, maker onboarding, banned account and preserved permissions. Check mobile flows. No password/recovery tokens should be logged. Verify email delivery with an actual test inbox.
## Existing accounts
Back up database; inventory verified emails, phone-only, unverified, Google-only, and admin/secondary-admin accounts. Keep legacy access until resolved. Never auto-confirm an unverified email or link by email alone. The migration script imports supported bcrypt hashes via Supabase Admin API for explicitly selected, already verified, non-admin accounts. Google-only eligible accounts receive a random unknown password; use recovery to set their own. No plaintext password is migrated.
Dry run: `node scripts/migrate-supabase-auth.mjs --user-id=<application-id>`
Apply only in approved maintenance window with the flag already tested: `FRESHPICK_AUTH_MIGRATION_APPROVED=true node scripts/migrate-supabase-auth.mjs --user-id=<application-id> --apply`.
Requires server-only SUPABASE_SECRET_KEY (or legacy service role key). Keep keys out of browser variables. A provider collision or ambiguous mapping stops for manual reconciliation. Preserve legacy hashes temporarily for controlled rollback; managed accounts cannot use legacy password or refresh flows. Old stateless access JWTs can remain valid until their expiry: shorten JWT_ACCESS_EXPIRES ahead of migration and wait out the previous maximum TTL, or plan an approved signing-key rotation with its session impact. Short-lived bridge access tokens expire within ten minutes even after provider logout/reset.
## Production gate
Do not enable production until staging end-to-end tests pass, SMTP works, RLS/data API exposure is reviewed, the migration and rollback are rehearsed, and admin MFA + verified email-change flows are implemented if required. Migrated users cannot simply fall back when the flag is turned off; handle rollback with explicit account recovery/reconciliation. No automatic production account migration or database change has been executed here.
